# Slim Maat private account integration (development only)

This isolated test app is not mounted in the original app. It can make real Supabase Auth requests if explicit public config is supplied, but is not release-ready. AI remains disconnected and email confirmation is not age verification. Do not deploy publicly or use real users until the security, privacy and end-to-end checks are complete.

The account screen links to a separate local tools preview, also included in the build. The two-player game and drawing board run locally without account access, network calls, sync or automatic storage. The drawing board can undo only the most recent stroke using one temporary in-memory image, where supported; clearing cannot be undone. A browser download is started only when requested; its completion cannot be verified here. The app asks the browser for a leave warning after drawing, but warnings are not guaranteed, especially on mobile; the warning remains even after an attempted download, until the drawing is cleared. The preview is not an account or age gate; load it while online. The service worker intentionally caches only the generic offline status page, not the tools or user data. Controlled navigations request `cache: no-store`, but the worker cannot protect the initial uncontrolled page, API responses, intermediary caches, or an older still-active worker. Before any hosted test, configure and verify appropriate server-side private/no-store headers and service-worker upgrade behavior. Browser offline testing is still outstanding.

Node 20 and pnpm are needed. In this directory run `pnpm install --frozen-lockfile`. Supply `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` through a local ignored `.env.local` or process environment; use only the intended Slim Maat project, never a secret/service-role key. Missing/invalid config or unavailable session storage disables the UI. Start `pnpm dev` on loopback. This private test stores the Supabase session in browser sessionStorage, scoped to the tab, to test recovery on reload. The browser can refresh tokens; the screen verifies the user with Supabase before showing signed-in state. Local signout clears that tab's session. Tokens in browser storage remain accessible to scripts running on that origin, so use a trusted private test environment only. This is not a final multi-device session design; URL session detection remains disabled.

Before a live test, configure Supabase email confirmation and suitable Site URL / allowed redirect URLs for the isolated test environment, and verify mail delivery and provider limits. The sign-up confirmation link uses the configured Supabase Site URL; opening it may land on a different page and does not automatically sign the user in. Log in after confirming. Supabase's default email service has restrictive limits and may only deliver to authorised team addresses. Never paste credentials or passwords into chat.

Installability foundation: the private account app has its own manifest and directory-scoped service worker. Deploy only in an isolated private environment using HTTPS, and configure any authentication and allowed redirects for that environment. Once opened online, the worker stores only a generic offline page. On failed navigation it shows that page; it does not cache account screens, tokens, API responses or personal conversations. Signing in, registration, AI and synchronisation do not work offline. Installation and offline fallback require testing on the actual device and protected deployment. Browser/platform rules may limit installability. The old mock preview is separate and is not this app.

For the limited production-backed sign-in test, the preview UI disables registration and does not call signUp. This is a UI limitation only, not a server-side registration restriction. Do not deploy with the production project until preview-only configuration and protected deployment are verified. Tests use mock clients: they do not prove email delivery or live authentication. A production launch still requires session persistence/refresh design, password reset, server-side token verification, independent adult eligibility, rate limits, moderation, RLS and retention/export/delete policy, redirect and SMTP configuration, security review and real end-to-end testing.
