# Conversation storage foundation (not deployed)

This is an isolated development prototype for future account-based conversation history. It is not wired into the app, not a migration in production, and does not enable AI, autosave, or sync. `history-schema.sql` proposes owner-scoped tables, row-level security, and cascade deletion. Signed-in clients may only insert user messages; assistant messages must come from a trusted server. `historyStore.js` is an unconnected browser adapter with basic validation and generic errors. Its current 100 conversation / 500 message result limits require pagination before release; it does not yet provide a complete export feature.

Before any deployment: independently review the SQL, privileges, indexes and database ownership; apply only in an isolated test database; test row policies and delete cascade against two real authenticated users and anonymous users, including attempts to insert foreign owner IDs, read/write/delete another user's data, forge assistant messages, bypass field limits and call after signout/revocation. Review the Supabase API configuration and RLS defaults. Include privacy notice, opt-in, retention, export and account deletion. Agree storage costs and abuse safeguards. Verify how the trusted AI backend associates assistant messages with the authenticated owner. Add pagination, concurrency behavior and error handling in the UI before describing history or sync as functional. Browser clients must never contain a service-role key. These checks do not replace server authentication or independent adult eligibility for AI.

Unit tests use a mocked client. They do not demonstrate actual database isolation, storage, AI calls, or cross-device sync. The current installed account app remains unchanged.
