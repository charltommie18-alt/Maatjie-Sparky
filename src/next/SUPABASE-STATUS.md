# Slim Maat: Supabase account preparation

A separate Supabase project has been created. Email sign-in and email confirmation are enabled. The site URL is still localhost and no redirect URLs are configured. The account boundary and browser setup in this directory are isolated and NOT mounted into the app. The official Supabase JS SDK is not installed, and no live signup/login flow has been tested. No app is connected just by creating this project.

`prepareSupabaseBrowserAccount` accepts an injected official Supabase `createClient` function, HTTPS hosted Supabase project URL and a public `sb_publishable_` key. It refuses missing or malformed config and secret/service-role or legacy JWT-style keys. Never store a private key or password in client code or the repository. It disables persistence, refresh and URL session detection deliberately for this preparation; sessions are not retained across reloads, email confirmation redirects and real workflows are NOT implemented. Do not deploy this as a complete login experience.

Before actual use: install and lock a compatible official SDK; build and test UI and session management, confirmation callbacks, a production site URL and explicit redirect allow-list. Configure custom SMTP for public users. Test end-to-end with test accounts. A successful signUp only indicates the request was accepted, not that the email is confirmed or the user may use chat; use neutral signup responses to reduce account enumeration.

Supabase login is not proof of age. Users must independently pass 18+ verification in server-controlled records inaccessible to user writes. Do not map getUser alone to adultAccess authenticated/revoked flags: an unexpired JWT can survive signout; use a server-side session existence check if immediate revocation is required. Implement rate limiting, origin/CSRF protection, user storage and RLS policies, opt-in consent, export and deletion. AI remains disabled until all controls are implemented and tested. Local signout does not sign out other devices.
