# Slim Maat: Supabase account preparation

A separate Supabase project was created with email sign-in and confirmation enabled. The site URL was last known to be localhost and redirect URLs were not configured; check these settings before hosted testing. The isolated development account app is not mounted into the original app. Its own package locks the Supabase SDK. Creating the project does not connect the original app.

`prepareSupabaseBrowserAccount` accepts an injected official Supabase `createClient` function, HTTPS hosted Supabase project URL and a public `sb_publishable_` key. It refuses missing or malformed config and secret/service-role or legacy JWT-style keys. Never store a private key or password in client code or the repository. By default persistence and refresh are off; the isolated test app explicitly uses tab-scoped sessionStorage with persistence and refresh. URL session detection is disabled. This is a development test, not a complete login experience or final multi-device session design.

For the app's setup and test limitations see `account-app/README.md`. Before hosted use: configure a suitable site URL and explicit redirect allow-list, verify confirmation and session recovery end-to-end using test accounts, and configure suitable SMTP for public users. A successful signUp only indicates the request was accepted, not that the email is confirmed or the user may use chat; use neutral signup responses to reduce account enumeration.

Supabase login is not proof of age. Users must independently pass 18+ verification in server-controlled records inaccessible to user writes. Do not map getUser alone to adultAccess authenticated/revoked flags: an unexpired JWT can survive signout; use a server-side session existence check if immediate revocation is required. Implement rate limiting, origin/CSRF protection, user storage and RLS policies, opt-in consent, export and deletion. AI remains disabled until all controls are implemented and tested. Local signout does not sign out other devices.
